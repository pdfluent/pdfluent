# PDFluent 1.0.0-beta.18 — Release Notes

> Internal release document (2026-06-19/20). Public-facing copy for
> pdfluent.com must go through the Humanizer skill before publishing.

**Why this release exists:** beta.17 shipped a **stale frontend bundle**
(`index-D6hf071_.js`) that predated the inline-editor fix, so editing white
text on a coloured background rendered the text invisible (white text behind an
opaque white overlay). The macOS artifact embedded the pre-fix bundle because
Tauri's `generate_context!` embed was not invalidated by a `../dist` change
under incremental builds. beta.18 ships the corrected bundle
(`index-E4bfMBnP.js`) and makes the stale-embed defect impossible to ship
again. **beta.18 fully supersedes beta.17 on the download page and updater.**

## Editor fixes

- **White text editing fixed.** The inline-edit overlay background is now
  `transparent` (was `#ffffff`); the rendered page (incl. coloured fills) shows
  through, so typed text lands in its true colour on any background. Verified on
  `Brainstorm.pdf` (white title on indigo): text readable, caret visible,
  typing/commit/cancel all correct, no opaque white rectangle.
- **DOCX export fixed (no more "unreadable content" / repair dialog).** Three
  defects resolved in the XFA SDK (`dc3513573`): embedded image media are now
  valid, decodable PNGs (was raw flate samples mislabelled `.png`); `styles.xml`
  uses the required `<w:name w:val="…"/>` attribute (was element text); tables
  no longer reference an undefined style and the body has a terminal `<w:sectPr>`.
  Every embedded media file decodes; the file opens cleanly in a freshly
  restarted Word.
- **Conversions run off the main thread.** `convert_to_docx/xlsx/pptx` are async
  (`spawn_blocking`), so image-heavy exports no longer freeze the UI.

## Release-pipeline hardening

- **Frontend-embed invalidation + gate.** `build.rs` fingerprints `dist` and
  forces a re-embed on any frontend change; `scripts/verify-frontend-embed.mjs`
  fails the build if a binary embeds a stale or missing bundle. The gate now runs
  in **every** real release path (`release-macos.sh`, `release-windows.ps1`,
  `.gitlab-ci.yml` build jobs, `build-verified.sh`) and has a CI test
  (`tests/verify-frontend-embed.test.ts`) that proves a deliberately-stale bundle
  fails.
- **No silent unsigned Windows release.** `release-windows.ps1` refuses to build
  an unsigned release MSI when the updater key is present but Authenticode signing
  is disabled.

## Signing & distribution

- **Windows MSI:** Authenticode-signed via **Azure Trusted Signing** (account
  `pdfluent`, profile `pdfluent-public-trust`, identity *Innovation Trigger
  B.V.*), Microsoft TSA timestamp. Verified Valid against the live artifact.
- **macOS DMG:** universal (Intel + Apple Silicon), **ad-hoc signed, NOT
  notarized** — Gatekeeper requires the documented right-click→Open bypass on
  first launch. Developer ID signing + notarization is a tracked P1 GA item, not
  done here.
- **Auto-update:** `latest.json` advertises beta.18 for `darwin-aarch64`,
  `darwin-x86_64` and `windows-x86_64` (Linux intentionally absent). Both updater
  signatures verify against the trusted key `9E2BAD9AABF995DD`; a beta.17 client
  is offered beta.18 and a beta.18 client is not looped.

## Known limitation (not a regression, not fixed here)

- **DOCX table-fidelity (P2).** `pdf-docx` over-columns text (≈one glyph per
  table column) for closely-spaced glyphs, so PDF→DOCX layout fidelity is poor
  even though the document is valid and opens without repair. Tracked separately;
  see `docs/known-limitations` / project memory.
