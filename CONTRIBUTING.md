# Contributing to PDFluent

Thanks for your interest in contributing to PDFluent. Here's how to get started.

## Getting started

1. Fork the repository
2. Clone your fork
3. Create a branch for your change
4. Make your changes
5. Run tests: `cargo test` (Rust) and `npm test` (frontend)
6. Open a pull request

## Development setup

PDFluent uses Tauri v2 with a React + TypeScript frontend and a Rust backend.

**Prerequisites:**
- Rust (stable)
- Node.js 20+
- Platform-specific Tauri dependencies (see [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/))

**Run locally:**
```bash
npm install
npm run tauri dev
```

The PDF engine is the PDFluent SDK, linked via Cargo path dependencies (see
`src-tauri/Cargo.toml`). The SDK workspace is licensed separately and isn't
included in this repository, so a full build requires access to it. See
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for how the pieces fit together.

## Code style

- Rust: follow `cargo clippy` suggestions
- TypeScript: ESLint config in the repo
- Commits: use conventional commits (`feat:`, `fix:`, `docs:`, etc.)

## Adding UI

Every control the interface offers must actually do something, and the build
checks it. `docs/UI_REGISTER.md` — generated by
`scripts/quality/ui-register.mjs`, verified by the `quality:ui-register` job —
maps each tile, panel, rail tool, palette command, button and advertised
shortcut to the command behind it and the test that proves it.

When you add or change a control:

1. Give it a handler that reaches a Tauri command or a named UI effect, and a
   `data-testid` if it is a button.
2. Write a test that names it, in `tests/` or `src/**/__tests__/` so a CI job
   runs it.
3. An All-tools tile also needs `fulfilledBy: '<kind>:<id>'` in
   `src/viewer/tools/toolDefinitions.ts`, naming the affordance that performs
   the tool. A tile whose claim does not hold is not rendered.
4. Run `node scripts/quality/ui-register.mjs` and commit the regenerated
   `docs/UI_REGISTER.md` and `src/viewer/tools/wiredTools.generated.ts` with
   your change.

If something has to ship in a gap state, record it in
`docs/ui_register_exceptions.json` with a reason. The gate fails on a gap that
is not recorded — and on an entry whose gap has since been closed.

- Keep PRs focused on a single change
- Include tests where applicable
- Update documentation if you change user-facing behavior

## Reporting bugs

Open an issue on GitHub with:
- Steps to reproduce
- Expected behavior
- Actual behavior
- OS and PDFluent version

## Community channels

- GitHub Discussions: https://github.com/pdfluent/pdfluent/discussions
- Discord: https://discord.gg/pdfluent

If you are new to the codebase, start with issues labeled **good first issue**.
